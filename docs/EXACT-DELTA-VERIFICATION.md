## Root cause and history

V11 calls `verifyDeterministic` before `verifyObjectiveAware` grants selected objective changes. The older authorization code pairs exactly one missing and one added date or number **globally**, requires a narrow target-verb/context match, treats a missing actor as authorized only when a single added name and an owner-style objective are found, and has no branch for hard negation or status findings. `runVerifiedCore` blocks remaining hard findings before the semantic verifier. Source facts retained elsewhere can erase the missing half of an occurrence-level delta; a multi-change sentence can produce several hard findings that the one-pair rule refuses to match. Thus the saved editor candidates were valid but the verifier returned or repaired back to source.

## Surgical V13 change

`src/lib/reconstruction/exact-delta-verification.ts` wraps the unchanged V11 result. It uses existing extracted claims and protected-value extractors to match a unique source occurrence, candidate replacement, and explicit objective target. It downgrades only the corresponding hard finding to `AUTHORIZED_CHANGE`; every other hard finding remains. For claim-level status/polarity changes, it requires matching source/candidate claim context and objective support for new content and negation. It also prevents an unrequested second actor or a one-predicate change in an unrelated claim from slipping past legacy warning-only checks during an explicit fact update. Ambiguous pairs remain blocked. This is selected only by `reconstruction-v13`, which keeps the V12 editor prompt and V11 semantic verifier/repair/fallback contracts. It adds no production route, editor prompt, planner, ontology, or type-wide license.

The exact-delta method is deliberately conservative. It can reject a candidate containing both a licensed and an unlicensed date change in one sentence without explicitly crediting the licensed half; the final safety outcome is still rejection. Its text matching cannot prove semantic equivalence. Semantic review remains necessary for warning-level changes, including some certainty transitions. A malformed or unavailable semantic response still fails closed.

## Limits and next step

These are small synthetic development probes. The new semantic-verifier and repair responses were produced by account-backed agents, not a paid API or a second independently verified model family. That is useful evidence for the decision boundary but is not a live production provider run. The independent auditor checked all 13 changed verdicts, all 14 unsafe boundary cases, all ten fresh cases, and all five fresh repairs. It found no new unsafe-boundary escape or incorrect fresh repair. It flagged `ea07`, a vague non-executable date-update request whose saved V12 **and** V13 replay both accept a repair that makes the old date tentative. The original label calls that unlicensed; the semantic verifier judged it permissible uncertainty signaling. This is a pre-existing interpretation dispute, not a V13 regression, and remains a limitation to inspect in the next actual-edit replay. The auditor also noted that `authorizedChangeCount` counts findings rather than semantic edits, `changeCount` is a legacy integrity count, and the trace's semantic verdict after repair is the final verdict rather than the initial one. The fresh manifest hashes are valid and were written before execution in this session, but a mutable local manifest is not an independent historical proof of blinding or freeze order.

No local model, holdout, deployment, or push was used. Incremental paid API spend: **$0**. Since known false rejections were removed and the original unsafe boundary stayed intact, the next task is **one fresh 30–50 case actual frontier-edit replay using V13**. That replay should inspect ambiguous vague-update repairs and actual objective satisfaction. Only after a healthy actual-edit replay should the analysis/verification architecture be frozen and blind Holdout V3 created in a later session.
