## One-time effort-selection mechanism, with no value selected here

An historical reviewer setting is not incorporated by the old manifest. A provider “default” can vary by model, time, account and client; provider guidance admits more than one task-appropriate effort. A task-complexity rule devised after seeing the old RAW/architectures would have discretionary cutoffs. Those options do not yield a unique, bias-resistant value. Choosing one now by judgment would violate the instruction to separate governance and value selection.

Instead, this successor preregisters a **public future randomness allocation** across the exact ordered list `low, medium, high, xhigh, max`. This list and order are fixed in the machine record **now** and cannot be shortened or reordered after the pulse. Before the pulse, a separate pre-draw lock must prove all five are supported and effective for the exact client/model/account and that every other non-effort execution field is fixed. Failure to prove any one level blocks the entire registration **before** the pulse, without drawing from a subset. This mechanism does not claim that the drawn level is optimal; it samples one supported reasoning regime and limits inference to that regime. It is impartial to A/B/C/D and all successor cases because the source pulse is unknown at registration and is drawn before any new case exists. There is no reroll for latency, cost, model behavior, outcome expectation, or a blocked effective setting.

**Pulse:** use only the [NIST Randomness Beacon 2.0](https://csrc.nist.gov/Projects/interoperable-randomness-beacons/beacon-20) signed pulse stamped **2026-10-15T00:00:00.000Z** (POSIX milliseconds **1792022400000**), from the exact `pulse/time/1792022400000` API endpoint. This registration and the pre-draw lock must both be committed before that target. The response must have exactly that `pulse.timeStamp`; a missing pulse, chain ambiguity, duplicate timestamp, invalid signature or unavailable certificate blocks the registration. There is no next-pulse substitution. Retain exact response bytes, chain/pulse identifiers, certificate bytes/hash, signature-verification method/result and SHA-256. Verify the signature using the Beacon 2.0 published signed-field serialization and certificate endpoint keyed by `certificateId`, and independently check the previous-pulse link and precommitment. The exact verification implementation and its hash must be in the pre-draw lock; if independent verification cannot be completed, BLOCK. Re-fetching the **same fixed pulse** for verification is permitted; changing the target is not. The future pulse is public, time-stamped and signed; NIST describes its 512-bit output and API. It is **not** used as a secret key. This is a locally committed registration; lack of an external timestamp limits the strength of an independently auditable time-priority claim and must be disclosed.

**Mapping:** hex-decode `pulse.outputValue` (case-insensitive) into **exactly 64 raw bytes**; reject any other length or non-hex character. For counter `i = 0, 1, ...`, compute `SHA-256(UTF8("whodunnit-post-v3-successor-effort-v1") || 0x00 || pulseBytes || uint32be(i))`; interpret the first four digest bytes as an unsigned big-endian integer `x`. With the fixed ordered list above, `n = 5`; accept the first `x < floor(2^32/5) * 5`; choose ordered index `x mod 5`. Store the pulse, exact eligible list, first accepted counter, integer, index, selected value and independent recomputation in an append-only execution lock. The value is determined when the pulse is published, whether or not a person computes it. Any abandonment or BLOCK after publication must disclose the pulse and resulting value, and any future registration on this question must disclose this attempted draw; no silent reroll. If source verification, supported-set proof or effective-request certification fails, **BLOCK** rather than draw again or choose another level. No successor case or output may be inspected to select, validate or replace the value. The later pass alone runs this mechanism and freezes its result.

This random design trades control over which effort is studied for an auditable, outcome-independent choice. Since effort can affect judgments and repairs, report the selected setting and do not generalize results to other levels. A future scientific preference for a particular level would require a *different* fresh preregistration before cases, not an amendment or a selective redraw here.

**Arithmetic test vector only:** for synthetic bytes `00 01 … 3f` (64 bytes), counter `0` yields SHA-256 `36976a6a2b464ef1767bf08245ede8dcada04fe80242aa25f0b3a919aed88f8f`, `x = 915892842`, and index `2` when `n = 5`. This synthetic vector is unrelated to the future NIST pulse and selects no experimental effort.
