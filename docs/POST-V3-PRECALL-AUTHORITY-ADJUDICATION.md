## Minimum controlling language

The original operational manifest's `futureCallPreflight.availability` says: “Before any call, re-confirm exact CLI version, alias resolution, account-backed $0 access, and effective settings.” Review and repair definitions require “pin exact resolved identity before any call.”

The settings clause requires the CLI's effective controls to be observed and pinned, including temperature, conditionally exposed top-p/top-k, thinking, maximum output, prompt/schema hashes and permission/tool/network configuration. Its consequence is: “If the exact effective settings cannot be observed and pinned, hard stop the affected run.”

The original network restriction is scoped to “model-call sessions” and allows an exception for “the CLI service connection.” The request/adapter hash must be frozen before calls.

The original authorization clause covers “future external generation, verification, repair, or review calls,” which require “separately recorded explicit run authorization,” confirmed account-backed zero-incremental-cost access, successful preflight and freezes. Its stage table assigns budgets to editor, semantic review, repair, recheck and blind-review requests. The failure rule describes “One attempt per budgeted request.”

The original `executionBoundary` states that operational registration does not “invoke any model” or “approve spend.” The preregistration separately says it “makes no calls and reserves no budget.” Neither original document explicitly names bootstrap GET acquisition or local request instrumentation. Neither forbids a new implementation-neutral proof mechanism that obeys the frozen conditions.

## Meaning of call and verification

Here “call” is read in the integrated caller/stage context: model/inference requests that generate, semantically verify, repair, recheck or judge experiment material. It is not silently expanded to every filesystem operation, CLI process or network packet. Otherwise the required pre-call availability/configuration verification would itself be confused with the model stages it precedes. This contextual reading does not permit a smoke inference: such a request is a model call regardless of being named a diagnostic.

The bootstrap GET retrieves account/model/client configuration. It does not perform the registered semantic verification of SOURCE/OBJECTIVE/RAW. Local genuine request construction captures configuration before dispatch; it does not obtain a model response. Thus neither method uses a semantic-review, repair or recheck call allocation. A disguised prompt submission, preliminary generated response or arm invocation would fall outside this classification and remain prohibited.

The strongest restrictive reading points to the lack of named metadata authorization and the service exception's model-session scope. That is a real distinction between an explicit action grant and an allowed method, but not an affirmative ban on metadata preflight. Scope, purpose and the exact model-stage descriptions support conditional methodological permission. Absence of the method's name alone is not declared irreducible ambiguity or an amendment requirement.

## Method A: bounded bootstrap acquisition

The registered native 2.1.288 client contains authenticated `/api/claude_cli/bootstrap` GET construction and local persistence of `client_data`, model access and account defaults. The prior static investigation found applicable account/catalog/client-data caches. It did not retrieve current remote metadata. Source also shows background bootstrap completion can replace required client-side settings before request construction; acquiring configuration is therefore relevant preflight evidence rather than an experiment outcome.

Method permission is limited to the existing registered account-backed CLI service dependency and required configuration evidence. It does not grant arbitrary internet access, another provider, API-key use, a newer CLI, model inference, external semantic verification, or changes to experimental material. A direct custom request is not automatically treated as equivalent to the registered client merely because its endpoint name matches: faithful method/path/provenance must be established before taking it.

Authentication is known historically as `claude.ai` Pro, with API-key routes excluded. That does **not** establish current zero incremental bootstrap billing. GET is non-inference, but HTTP verb, absence of generated text and account-backed authentication do not prove price. **Bootstrap billing is UNKNOWN.** No claim of $0 acquisition is made; the applicable zero-incremental-cost condition must be confirmed before a future authorized acquisition. If that confirmation cannot be obtained, the action remains blocked without changing the method adjudication.

Fetching a service resource is remote communication, not demonstrated modification of remote account policy. An ordinary client fetch may update local user caches/configuration. Those local writes are separate from changing remote state and from mutating frozen experiment evidence. Neither possible local cache refresh nor read-only HTTP semantics prove that every side effect is absent. Any future bounded acquisition must preserve the registered experimental files, credentials privacy and durable provenance; it must not represent changed local cache bytes as previously observed evidence.

The previously inspected bootstrap constructor sends client entrypoint/model/version and account authentication context; no SOURCE, OBJECTIVE, RAW, prelabels or outcome payload was identified in that GET construction. This supports bounded classification, not a blanket promise that every CLI startup path sends only metadata. A future implementation must exclude experimental case text from acquisition and retain only necessary nonsecret configuration evidence. Endpoint, registered binary/version, timestamp, response byte/hash provenance, and the sanitized fields actually contributing to model/settings resolution must be retained sufficiently to reproduce the proof. Secrets and account identifiers must not be published. These are applications of the original hash/provenance/settings requirements, not permission to fabricate a response or keep only a boolean proof flag.

## Method B: genuine local pre-transport capture

Local evaluation of genuine client functions is stronger observation of required effective state, rather than a relaxation of it. A modified copy or instrumentation may be used only as inspection tooling, with fidelity to the registered binary's construction logic established. The installed registered binary, experimental arms, prompts/settings contract and frozen artifacts remain unchanged.

The inference boundary must be disabled before executing code that can dispatch. A claimed expectation of no request, a localhost proxy alone, or interception after transmission is insufficient. If this method is classified as entirely local, any metadata/telemetry/auth network activity must also be prevented; remotely acquiring state is Method A and needs its separate constraints. No model request can leave the machine and no generated model output may be obtained.

Network-denied startup can select a cached/failure branch. Such a captured payload is evidence of that branch, not automatically evidence of the future normal bootstrap-enabled path. Stubbing a guessed response cannot establish the active state. A truthful certificate must identify the actual pinned inputs and show they apply to the exact future invocation. This authority decision neither chooses a technical binding design nor promises that a faithful complete certificate can be produced.
